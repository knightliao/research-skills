# 代码分析边界规则

## 事实、范围与未知

- 代码直接定义或框架具有明确语义的行为作为事实陈述。
- 由命名和上下文支持但未直接证明的结论使用“从当前调用位置看”“可能”等限定语。
- 先判断输入是完整程序还是局部片段；片段没有入口时说明外部调用边界，不任选第一个函数当入口。
- 多个外部实现缺失时集中说明共同边界；只有未知会改变当前行为理解时才在局部重复。
- 语言、框架、部署环境或运行结果证据不足时保持未知。

## 入口与执行顺序

优先寻找 `main()`、直接执行保护、Web 路由、命令处理器、生命周期钩子、回调、事件监听器、Tool 和任务 worker。说明谁在什么条件下触发它。

核心流程按运行顺序写，详细分析按源码顺序写。imports、模型和 helper 必须覆盖，但不因位于文件前部就占据主路径开头。

## 选择主要解释视角

只选择最能降低理解成本的主要视角：

- **调用链**：难点是多个函数、服务或层级如何协作。
- **数据流**：难点是输入如何转换为输出。
- **状态迁移**：难点是对象状态何时、为何变化。
- **分支结果**：难点是提前返回、异常、重试或降级产生不同结局。
- **生命周期**：难点是初始化、运行、提交、清理等阶段。

不要为了显得完整同时输出所有视图。第二种视图必须解释第一种无法表达的重要关系。

## 控制、数据、状态与副作用

分析每个语义单元时，只解释实际发生变化的维度：

- 控制：下一步去哪，哪些路径被阻止或提前结束；
- 数据：值来自哪里、如何转换、被谁消费；
- 状态：哪个对象从什么状态变为什么状态；
- 副作用：网络、文件、数据库、缓存、队列、事件或共享对象发生什么可见变化。

不要只复述条件真假。关键分支说明触发条件、终止了什么、最终结果是什么。

## 异步与事件驱动

首次遇到 `await` 时，可结合上下文说明等待异步操作；后续不重复科普。不能仅凭 `async` 断言一定并发，也不能把同步调用描述为非阻塞。

回调、路由、事件监听器和 Tool 的定义不会自行执行；说明其外部触发边界。取消、超时和普通异常会导致不同结局时，分开表达。

## 外部依赖

对当前输入未实现的函数、模块或服务，只说明：

1. 调用位置；
2. 当前可见输入；
3. 返回值或异常在本地流程中的用途；
4. 当前片段无法确认的底层部分。

例如 `send_event(data)` 只能确认尝试发送事件，不能在无证据时指定 Kafka、HTTP 或云服务。

## 重复、注释与不可达内容

- 重复结构按共同模式归并，但单独指出会改变行为的条件、状态或返回值差异。
- 注释是理解线索；与代码冲突时，以实际行为为准并简要指出差异。
- 当前片段未使用的内容只能写“当前片段未看到后续使用”，不能断言整个项目从未使用。
- 明显不可达的路径可说明实际控制流，但不延伸为删除或重构建议。

## 长代码分配策略

开始写作前先完成完整结构地图、真实入口、主路径、关键分支以及重要数据和状态关系。

整体目的和主路径必须完整，结构地图必须覆盖全局；详细深度优先分配给入口、状态变化、关键分支、跨结构调用和外部副作用。配置表、重复映射和样板定义可以批量概括，但必须保留差异和覆盖状态。
