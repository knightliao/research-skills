# 反面代码分析示例

以下示例用于识别常见失败模式，不要复制其中的错误写法。

## 示例代码

```python
async def load_user(token):
    response = await client.post(
        AUTH_URL,
        headers={"Authorization": token},
        timeout=5,
    )
    return response.json()
```

## 失败一：用技术栈代替代码目的

> 这段代码使用 Python 异步函数和 HTTP Client。

这只描述了实现形式，没有回答代码为什么存在。更好的整体说明应指出：当前片段根据 Token 请求并返回用户数据；认证服务的内部实现仍未知。

## 失败二：机械逐行翻译

> L2 调用 `post`。<br>
> L3 传入 `AUTH_URL`。<br>
> L4 传入 `headers`。<br>
> L5 设置 `timeout`。<br>
> L6 关闭括号。

L2-L6 共同组成一次请求，必须作为一个语义单元解释。完整覆盖不等于每个物理行单独输出。

## 失败三：臆测外部实现

> 这里查询 Redis 中的用户缓存，缓存未命中后访问 PostgreSQL。

代码只显示调用 `client.post()` 获取响应，没有 Redis 或 PostgreSQL 证据。这些底层机制必须保持未知。

## 失败四：从 L1 开始念，忽略主路径

> 第一步定义 `load_user()`，然后创建 `response`，最后返回 JSON。

这没有先建立调用目的、触发边界和数据流，也没有说明等待网络结果以及返回值将交给外部调用方。若代码来自更长文件，核心流程应先寻找真实入口，不能把源码第一项定义自动当作执行起点。

## 失败五：核心流程缺少可扫读概括

> 1. `get_article()` 调用 `fetch_user()`。<br>
> 2. `fetch_user()` 调用 `client.post()`。<br>
> 3. 然后调用 `can_read()`。

这只是函数列表。即使用户逐句阅读，也很难快速看出每个阶段承担什么职责。应改为“**接收文章请求**”“**获取用户身份**”“**校验读取权限**”等并列的动作概括，再用一句话补充必要流向。

## 失败六：前详后略但声称完整

> 已逐行分析 L1-L100。其余 800 行篇幅有限，后续可继续。

即使标出了遗漏范围，用户仍不知道后 800 行的职责。长代码必须先提供覆盖整个输入的模块地图和完整主链路，再如实标注哪些模块尚未展开。

## 失败七：偷偷变成 Review

> 建议增加重试、改用指数退避并把 Client 注入函数，以提高可测试性。

这些可能属于 Review、优化或重构，不属于“看懂代码”。除非直接影响实际行为解释，否则不得主动给修改建议。

## 失败八：把单函数硬拆成系统模块

> 模块一：参数模块。<br>
> 模块二：条件模块。<br>
> 模块三：返回模块。

单个函数通常更适合按“前置检查、主处理、结果返回”等逻辑阶段解释。结构名称必须反映代码真实形态，不能为了套模板制造不存在的架构。

## 失败九：重复同一个结论

> 一句话说明：这里验证用户。<br>
> 核心流程：这里验证用户。<br>
> 模块职责：这里验证用户。<br>
> 逐行解释：这里验证用户。

完整结构不等于重复内容。一句话说明整体目的，核心流程说明顺序和分支，详细分析只补充具体语句如何实现验证。

## 失败十：同时堆叠所有关系图

> 下面分别给出调用链、数据流、状态图、异常树和生命周期图。

如果调用链已经能解释理解难点，其余图只会增加阅读成本。默认选择最有价值的一种视角，第二种必须带来明显新增信息。
