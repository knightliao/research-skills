# 代码分析

帮助用户用尽可能低的阅读成本建立准确的代码心智模型：先明确目的和主路线，再解释结构、分支、状态与实现细节。

## 调用边界

- 仅在用户通过 `$analyze-code` 或当前宿主的 Skill 入口明确选择后使用。
- 禁止隐式调用；用户只表达解释、看懂或分析意图，或只粘贴代码时，不得自行启用本 Skill。
- 用户显式选择本 Skill 后，即使没有附加说明、只粘贴代码，也直接分析。
- 用户主要要求修改、调试、找 Bug、Review、安全审查、性能优化、重构或生成测试时不使用。
- 用户同时要求理解和其他任务时，只完成已经明确选择的理解任务；转入其他任务时遵守当前宿主路由与用户授权。

## 输入处理

- 接受“可选自然语言上下文 + 代码正文”的自由文本，不要求 JSON、语言、框架、文件名或入口参数。
- 优先把 Markdown 代码围栏中的内容识别为代码；没有围栏时，根据语法、缩进和用户说明识别。
- 第一版只分析当前消息的一段代码。多个片段明显连续时可合并；多个目标互不相关且无法判断时，再请求用户指定。
- 保留代码正文的原始字符、顺序和空行，不先格式化、修复或重排。

用户询问如何使用、要求可复制输入、显式选择后没有提供代码，或需要说明边界时，读取[用户使用示例](examples/usage.md)。不要每次默认读取。

## 分析工作流

1. **锁定分析范围**：分离上下文与原始代码，判断它是片段、单函数、类、完整文件还是框架处理器，并建立稳定行号。
2. **识别已有证据**：在证据充分时识别语言、框架和技术栈；不足时保持未知。
3. **建立全局结构**：通读全部代码，按真实形态建立逻辑阶段、职责与方法、文件模块或入口处理链地图。
4. **寻找真实入口**：区分源码顺序与执行顺序；识别直接入口、路由、回调、事件、Tool 或外部调用边界。
5. **选择解释视角**：判断理解难点主要是调用关系、数据转换、状态迁移、分支结果还是生命周期，优先使用最有价值的一种视角。
6. **还原执行路径**：先写正常主路径，再单独整理真正改变结果的取消、异常、提前返回和降级分支。
7. **规划语义覆盖**：把所有有实际语义的原始行归入语义单元；入口、关键分支、状态变化和外部副作用详细解释，简单定义与连续赋值批量概括。
8. **生成分析结果**：默认使用简体中文，严格遵守[输出契约](references/output-contract.md)。遇到异步、事件驱动、重复分支、外部实现、注释冲突或长代码时，再读取[分析边界规则](references/analysis-guidelines.md)。

首次校准、发现输出机械或修订本 Skill 时，可对照[优质分析示例](examples/good-analysis.md)和[反面分析示例](examples/bad-analysis.md)。不要复制示例篇幅或框架细节。

## 信息密度原则

- 一句话说明只承载整体目的；核心流程只承载执行顺序、关键分支和最有价值的关系；详细分析只补充局部实现机制。
- 同一事实默认只完整解释一次。详细部分提到上文结论时，只说明当前代码如何实现它，不重新讲整条流程。
- 完整语义覆盖不等于平均篇幅。简单代码可以合并，但任何影响数据、状态、控制流或外部世界的差异都不能隐藏。
- 解释代码在当前可见流程中的作用，不猜测作者动机。无法确认的信息集中、简洁地说明，避免每段重复免责声明。

## 原始行号与覆盖

- 从代码正文第一行开始编号为 `L1`；围栏和代码外说明不计入，代码内部空行保留位置但不单独解释。
- 多行调用、链式表达式、数据结构和函数签名使用 `Lx-Ly` 合并解释；闭合符号并入所属单元。
- 所有 import、定义、赋值、分支、循环、异常处理、返回、调用、I/O、状态修改和数据转换都必须进入某个语义单元。
- “逐行”表示完整语义覆盖，不表示每个物理行单独输出，也不表示每个单元使用同等篇幅。

## 长代码与输出预算

- 整体目的和主执行路径必须完整，结构地图必须覆盖整个输入；只有局部解释深度可以缩放。
- 详细分析不能只展开文件前部。预算不足时，优先解释入口、关键分支、状态变化、跨结构调用和外部副作用。
- 对已展开、部分展开和未展开的结构标明名称与行号范围，不得静默遗漏或把未展开内容写成已完整分析。

## 静态分析边界

- 默认不运行代码、不访问网络、数据库或外部服务、不修改文件，也不假定代码能够成功运行。
- 不主动输出 Bug、质量评价、安全风险、性能建议、重构方案或测试方案；只在影响行为理解时中性说明相关事实。
- 对外部函数、模块和服务，只说明当前代码能确认的调用、可见输入及本地用途，不猜测底层实现。
- 明确区分事实、合理推断和未知；注释与代码冲突时以实际行为为准，不借此扩展成 Review。

## 完成前检查

1. 用户只看一句话和加粗流程概括，能否说出代码目的和主路线？
2. 使用的是符合代码形态的结构地图，还是把单函数硬拆成了多个模块？
3. 是否选择了最有价值的调用、数据、状态、分支或生命周期视角，而不是全部堆上？
4. 正常主路径和改变结果的关键分支是否分开表达？
5. 所有语义行是否被覆盖，且解释密度是否按认知价值分配？
6. 同一结论是否只完整解释一次，局部分析是否提供了新信息？
7. 事实、推断和未知是否清楚，是否保持静态理解边界？
