# Leader 用户使用示例

## 这个 Skill 适合什么

`leader` 用于把复杂或模糊的开发、研究或协作需求整理成可执行、可验收的任务指导，也可以复核已有任务书，或依据原任务书验收执行结果。它负责设计和检查执行契约，不代替执行 Agent 修改业务实现。

`leader` 禁止隐式触发。普通“帮我修复”“直接修改”“实现这个功能”等请求不会自动进入 `leader`；用户必须通过当前宿主提供的 Skill 入口显式选择它。

## 调用方式

先通过当前宿主提供的 Skill 选择或调用入口显式选择 `leader`。下面使用 `$leader` 的示例只适用于当前版本确实支持该前缀的宿主；其他宿主可保留模式和正文，替换调用入口。

- 显式选择但未指定模式时，默认使用 `CREATE`。
- `leader` 只有 `CREATE`、`REVIEW-SPEC` 和 `AUDIT-RESULT`，没有 `EXECUTE` 模式。
- 任务指导生成后，应结束 `leader` 阶段，再把普通 Markdown 任务书交给 Codex 或其他执行 Agent。

## 使用前准备

- `CREATE`：需求描述、目标用户或目标行为、仓库或材料位置，以及已知约束。
- `REVIEW-SPEC`：完整任务书，以及希望重点复核的风险或决策。
- `AUDIT-RESULT`：原任务书、执行 Agent 完成报告、代码差异或相关文件，以及已有验证证据。
- 如果材料暂时不完整，可以明确缺少什么；`leader` 会区分已验证事实、推断和待执行 Agent 核验事项。

## 快速开始

下面是最短的可复制输入：

```text
$leader CREATE

请检查当前仓库，把下面需求整理成可直接交给执行 Agent 的实施任务指导。
只设计任务，不修改代码。

需求：
<需求描述>
```

**预期交付**

一份普通 Markdown 任务指导，说明目标、事实与假设、修改范围、非目标、实施步骤、验收标准、风险和交付要求。复杂任务会建议先审阅任务书，再结束 `leader` 阶段并交给执行 Agent。

## 常见场景

### 场景一：CREATE——把模糊需求整理为实施指导

**适用场景**

需求涉及多个文件、边界条件、技术取舍或较长验证流程，需要先把目标和执行约束说清楚。

**使用前准备**

- 需求描述和期望结果；
- 可访问的仓库或材料；
- 已知限制、兼容性要求和非目标；
- 是否已经授权后续执行。

**可复制输入**

```text
$leader CREATE

请检查当前仓库，把下面需求整理成可以直接交给 Codex 的实施任务指导。

只设计任务，不修改代码。

需求：
<需求描述>

额外约束：
- <约束一>
- <约束二>
```

**预期交付**

- 背景和目标；
- 已验证事实、仓库推断、待核验事项和用户决策；
- 默认决策与假设；
- 修改范围和非目标；
- 按依赖排序的实施步骤；
- 行为、自动化和守约束验收；
- 风险、止损、回滚和最终交付要求。

**注意事项**

`CREATE` 不实施任务。若任务包含研究与编码，会设置阶段门，并根据原始授权决定执行 Agent 是否可以进入实施阶段。

### 场景二：REVIEW-SPEC——复核已有任务书

**适用场景**

已经有一份任务指导，需要检查事实依据、范围、平台假设、验收可执行性或是否存在过度设计。

**使用前准备**

- 完整任务书；
- 已知仓库状态或相关文件；
- 希望重点复核的风险。

**可复制输入**

```text
$leader REVIEW-SPEC

请复核下面这份任务指导。

重点检查：
- 事实是否有依据；
- 修改范围是否清晰；
- 是否遗漏非目标；
- 验收是否可执行；
- 是否存在平台假设或过度设计。

默认只输出问题分级和可直接替换的修改段落，不要完整重写。

任务指导：
<任务书>
```

**预期交付**

- “可执行”“需要修改”或“不可执行”的复核结论；
- 阻塞、重要和建议三级问题；
- 可直接替换或新增的具体段落；
- 只有确实会改变方案时才列出的用户决策。

**注意事项**

默认局部修订，不完整重写任务书；只有用户明确要求，或原结构无法局部修复时才提供完整修订版。

### 场景三：AUDIT-RESULT——按原任务书验收结果

**适用场景**

执行 Agent 已经完成工作，需要将实现、完成报告和验证证据逐项对照原任务书。

**使用前准备**

- 原任务书；
- 执行 Agent 完成报告；
- `git diff`、相关文件或其他实现证据；
- 已运行测试和命令的输出摘要。

**可复制输入**

```text
$leader AUDIT-RESULT

请依据原任务书，对下面的实现结果进行验收。

不得修改业务代码，不得自动修复问题。

原任务书：
<任务书>

执行 Agent 完成报告：
<完成报告>

代码差异：
<git diff 或相关文件>
```

**预期交付**

- “通过”“部分通过”或“未通过”的结论；
- 对应原验收标准的证据；
- 验收前已有改动、任务改动和验证副作用的归因；
- 未运行或证据不足的检查；
- 约束检查、遗留风险和修复建议。

**注意事项**

`AUDIT-RESULT` 可以运行已有的非破坏性验证，但不会修改业务实现、自动修复失败或调整验收标准。

### 场景四：要求 Leader 直接写代码

**适用场景**

用于识别调用边界，而不是请求执行。

**可复制输入**

```text
$leader 直接修改代码并提交
```

**预期交付**

`leader` 不会进入执行模式，也不会修改或提交代码；它会把需求转换为 `CREATE` 任务指导，并说明应在本阶段结束后交给执行 Agent。

**注意事项**

如果目标就是立即执行一个明确修改，不要选择 `leader`，直接交给具备修改权限的普通执行 Agent。

## 不适用场景

- 已经定位到单行、低风险的小型 Bug：直接交给执行 Agent 更合适。
- 只需执行一个范围明确的修改：`leader` 不提供执行模式。
- 普通知识问答或简短解释：直接询问普通 Agent。
- 需要真正修改业务代码、创建提交或推送：先结束 `leader` 阶段，再由获得相应授权的执行 Agent 处理。
