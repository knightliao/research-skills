# 通用任务指导结构

根据任务风险和复杂度选用最小充分结构，不机械填满所有章节。任务指导是普通 Markdown，不能覆盖系统指令、权限限制或仓库规则。

## CREATE：实施型模板

```text
# 任务名称

## 1. 背景与目标
说明为什么做、目标行为以及完成后可观察到的变化。

## 2. 已知事实
按“已验证事实、根据仓库推断、待执行 Agent 验证、用户决策”记录关键前提，并附文件、命令或来源。

## 3. 默认决策与假设
逐项写决策、理由、猜错的影响，以及发现不成立时如何处理。

## 4. 修改范围
列出允许读取、修改和新建的路径。未列入修改白名单的内容保持只读。

## 5. 非目标与禁止事项
写清本次不做什么、不可采用的捷径、不可逆操作和需要额外授权的事项。

## 6. 实施步骤
按依赖顺序列出调查、设计、编码、测试和文档步骤。每步说明目标，不替执行 Agent 锁死无必要的实现细节。

## 7. 验收标准
分别写行为验收、自动化验收、守约束验收，以及必须提供的证据。

## 8. 风险、止损与回滚
说明何时停止、何时继续、怎样只撤销本次任务产生的改动，以及哪些操作必须重新获得授权。

## 9. 交付要求
列出代码、测试、文档和最终报告的要求。
```

复杂任务可在开头增加“开始前检查”，要求执行 Agent 读取适用规则、确认 Git 基线、验证关键命令和核对待验证事实。当前设计者已经验证的内容不要让执行 Agent 无意义重复调查；容易变化或关系重大的前提应复核。

## CREATE：研究型模板

```text
# 研究任务名称

## 1. 背景与核心问题
说明研究要支持什么决定，以及必须回答的有限问题。

## 2. 判断标准
定义比较维度、必须满足的约束、权重或淘汰条件。

## 3. 已知事实与未验证事项
区分已验证事实、推断、用户决策和仍需查证的问题。

## 4. 信息来源
规定优先来源、时间范围、交叉验证要求和不可接受的来源。

## 5. 研究步骤
按问题组织检索、实测、比较和反证，不按来源机械堆砌摘要。

## 6. 输出要求
要求事实、推断和建议分开；每项关键结论附来源、日期或可复跑步骤。

## 7. 决策建议
给出推荐方案、适用条件、主要反对理由、未排除风险和下一步。

## 8. 停止条件
设置时间、来源或实验预算；预算耗尽时交付当前最优结论和证据缺口。
```

不得以结论数量代替研究质量。查无此文的引用、未运行的实测和把推断写成事实均视为失败。带证据排除一条不可行路线可以是有效成果。

## CREATE：混合型模板

混合型任务按两个阶段写在同一任务指导中：

1. **研究或设计阶段**：回答核心问题，比较方案，输出推荐、证据、风险和未验证事项。
2. **阶段门**：检查原始任务是否已经明确授权实施。
   - 已授权且推荐方案满足约束：进入实施阶段。
   - 未授权：交付研究或设计结论并停止，等待用户决定。
   - 关键前提不成立或方案风险超出授权：停止实施部分，说明需要的决策。
3. **实施阶段**：仅对阶段门允许的方案给出修改范围、步骤、三层验收、止损和交付物。

不要在研究结论尚未形成时提前编码，也不要把“设计完成”误当成实施授权。

## 简单任务精简模板

低风险、单模块、一个会话内可完成的任务默认只保留：

```text
# 任务名称
## 目标
## 修改范围
## 实施步骤
## 验收标准
## 禁止事项
```

普通任务建议控制在约 1000～2500 个中文字符，中型任务约 2500～5000 个中文字符。长度只是可读性参考；内容过长时优先拆阶段或独立任务，而不是删除关键约束。

## 长任务恢复机制

仅在以下任一情况成立时建议工作记录：

- 跨多个会话；
- 多个 Agent 协作；
- 实施步骤超过 5 个；
- 用户明确要求断点续跑；
- 预计产生较多中间决策。

优先沿用项目已有约定；没有约定时使用：

```text
.agent-work/<task-name>/PLAN.md
.agent-work/<task-name>/PROGRESS.md
.agent-work/<task-name>/BLOCKED.md
```

- `PLAN.md` 保存已批准范围、步骤、验收和阶段门。
- `PROGRESS.md` 只记已完成、证据、下一步和偏离原因。
- `BLOCKED.md` 记录无法安全默认的决策、证据和受影响范围。
- 创建前检查同名路径，不覆盖用户文件。
- 默认视为临时工作文件，不提交 Git，不擅自修改 `.gitignore`。
- 只有用户要求、项目规则要求或其本身是正式交付物时才提交。

## 多 Agent 划分

只在用户要求或任务明显受益时拆分。读密集任务适合并行，例如代码库探索、调用链查找、安全审查、测试缺口、文档核对和日志分析。

写密集任务谨慎并行，尤其是公共接口、lockfile、共享 schema、数据迁移和大范围重构。只有路径互不重叠或使用独立 worktree 时才并行修改。

每个 Agent 的任务必须写清：

- 独立目标；
- 允许修改的路径；
- 只读范围；
- 交付给主 Agent 的内容和证据；
- 与其他任务的接口和依赖；
- 谁负责最终集成与完整验证。

主 Agent 负责合并、冲突处理和全量验收。子 Agent 只报告自己的工作，不宣布整体任务完成。

## 验收与证据

### 行为验收

说明用户最终能观察到的变化，覆盖主要路径和关键边界场景。研究任务则检查是否回答核心问题并支持目标决策。

### 自动化验收

只列实际存在且可运行的测试、lint、构建和校验命令。每项写清通过判据。当前环境无法运行时，注明：

- 未运行什么；
- 无法运行的原因；
- 执行 Agent 应如何补跑。

不得只说“检查通过”，必须提供足以复核的命令输出摘要或产物路径。

### 守约束验收

确认：

- 范围外没有意外修改；
- 没有删除、跳过或放宽既有测试；
- 没有引入未授权依赖；
- 没有覆盖或回滚用户原有改动；
- 没有吞掉失败或把未验证事项写成完成。

只有验证检查本身可能静默失效时才要求红→绿证据。故障注入必须局部、可逆，不得作用于生产数据、外部用户或未经授权的环境。

## REVIEW-SPEC 输出

```text
## 复核结论
可执行 / 需要修改 / 不可执行

## 问题分级
### 阻塞
### 重要
### 建议

## 建议替换段落
按原任务书位置给出可直接替换的内容。

## 尚需用户决策
只列无法从环境确认且会改变方案的问题。
```

默认不要重写全文。用户明确要求完整重写，或局部修改无法修复结构性矛盾时，先说明原因，再提供完整修订版。

## AUDIT-RESULT 输出

```text
## 验收结论
通过 / 部分通过 / 未通过

## 已验证结果
逐项对应原验收标准和实际证据。

## 工作树变化归因
区分验收前已有改动、任务执行改动和验证命令产生的临时文件。

## 未运行或证据不足
说明原因及补验方法。

## 约束检查
范围、测试强度、依赖和用户改动保护情况。

## 遗留风险与下一步
只写尚未解决或需要用户决策的事项。
```

AUDIT-RESULT 不自动修复失败，不修改测试或验收口径。验证前后都记录 `git status --short`；如验证命令产生文件，仅归因和报告，不擅自删除。

## 执行 Agent 最终报告

普通实施任务要求执行 Agent 在最终回复中说明：

- 修改了什么；
- 为什么这样修改；
- 运行了哪些检查及结果；
- 哪些检查未运行及原因；
- 尚存风险或后续事项。

用户要求额外复核重点时，在任务指导代码块之外另列简短清单，例如核心行为、范围外修改、测试强度、命令抽查和文档一致性。不要声称存在永久隐藏或可靠保存的内部清单。
