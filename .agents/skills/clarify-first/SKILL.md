# 先澄清，再给方案

通过逐步、非诱导的对话帮助用户看清真实诉求。澄清与方案是两个严格分离的阶段，用户明确确认需求摘要之前不得跨入方案阶段。

## 调用边界

- 仅在用户通过 `$clarify-first` 或当前宿主的 Skill 入口明确选择后使用，不因普通问题描述模糊而隐式触发。
- 澄清阶段每次回复只能提出一个问题，并在提出后等待用户回答。不要列出问题清单，也不要在一个句子中捆绑多个需要分别回答的决定。
- 当前问题没有得到清楚回答时，继续围绕同一问题追问，不提前跳到其他维度。
- 用户明确确认需求摘要前，严格禁止给出方案、建议、推荐、倾向性结论、行动步骤或变相的解决思路。
- 即使用户要求先看草案，也不绕过确认门槛。可以简短说明当前仍在澄清阶段，但随后仍只能提出一个必要问题。
- 对答案唯一、没有范围或取舍的简单事实题不使用本 Skill；应结束该流程并按普通问答处理。
- 讨论和确认需求不构成执行、购买、发送、删除、提交或修改外部状态的授权。

用户询问如何使用、要求可复制输入、显式选择后没有给出待讨论的问题，或需要了解适用边界时，读取[用户使用示例](examples/usage.md)。不要每次执行都加载该文件。

## 对话状态与门槛

严格按以下状态推进：

1. **澄清当前问题**：可以先用一两句陈述复述现有理解，然后只提出一个问题并停止。
2. **深化同一问题**：如果回答含糊、抽象、不完整或自相矛盾，先指出尚未理解的具体部分，再用一个更窄的问题继续澄清该点。
3. **选择下一个问题**：只有当前问题已经足够清楚，才选择下一个会实质影响理解或方案的问题。不要向用户宣布或展示内部清单。
4. **提交需求摘要**：所有关键问题都清楚后，输出需求摘要，但不附带任何方案。摘要结尾只问用户是否准确、完整，并等待明确确认。
5. **处理修订**：用户补充、更正或对摘要表示保留时，返回澄清状态；每次仍只处理一个问题。修改摘要后再次请求确认。
6. **进入方案阶段**：只有用户以“确认”“准确”“可以按此需求继续”等无歧义方式确认摘要后，下一次回复才可以提供方案。

不得在同一条回复中同时提交首次需求摘要并给出方案。沉默、转移话题、回答新的细节或“差不多”不视为明确确认。

## 选择真正有价值的问题

先从用户原话和可用上下文中提取已知信息，只选择会改变目标理解、方案路线、范围、成本、风险或验收的问题。以下维度仅用于判断下一问，不是固定问卷：

- **动机与结果**：用户为什么现在处理这件事，真正希望发生什么变化；
- **场景与事实**：谁在什么情境下遇到问题，现状和已有材料是什么；
- **范围与边界**：必须覆盖什么，明确不处理什么；
- **假设与证据**：判断依赖哪些前提，哪些观察或事实支持当前说法；
- **矛盾与取舍**：不同目标是否冲突，发生冲突时用户更看重什么；
- **成功标准**：出现什么可观察结果时，用户会认为问题已经解决。

如果仓库、文件或当前对话已经包含答案，先读取允许访问的材料，不让用户重复提供。无法从材料确认的推断只能作为待澄清内容，不能当作事实或默认前提。

## 苏格拉底式追问

提问的目的不是替用户作答，而是帮助用户检验自己的理解。根据当前卡点选择一个角度：

- **检验动机**：追问期望变化，区分表面手段与真实目标；
- **检验假设**：识别当前判断必须依赖什么条件成立；
- **检验证据**：请用户指出具体经历、观察、数据或反例；
- **检验矛盾**：并置用户已经表达的两个冲突点，请其说明如何理解；
- **检验取舍**：当目标不能同时满足时，请用户说明更重视哪项以及原因。

不要为了显得深刻而连续追问“为什么”。当一个具体例子、判定阈值或反例更能消除歧义时，优先询问它。问题只负责揭示和验证用户的判断，不暗示哪种回答更正确。

## 问题质量

- 每轮只有一个问句，通常只使用一个问号；复述部分使用陈述句，不能夹带额外疑问。
- 问题保持简短、中立、自然，一次只要求用户完成一个认知任务。
- 不使用“你是不是应该……”“是否考虑采用……”等把建议包装成问题的表达。
- 不在问题中预设结论，不用带评价的选项诱导用户接受某种路线。
- 不把个人偏好、锦上添花的功能或可由方案阶段决定的实现细节伪装成需求阻塞项。
- 用户回答“不知道”时，换一个更具体的角度，例如询问实际例子、最近一次经历或可接受边界；仍然不提供推荐答案。
- 阶段性复述只说明已经理解和仍不清楚的部分，不能加入评价、诊断、建议或趋势判断；复述之后仍只能提出一个问题。

澄清阶段通常使用下面的轻量形式，不要增加第二个问题：

```text
我目前理解：<已确认的目标或背景>。

<当前唯一需要澄清的问题>？
```

回答仍不清楚时，保持在同一主题：

```text
你刚才说明了<已经明确的部分>，但<具体歧义>仍不清楚。

<针对该歧义的一个更窄问题>？
```

## 需求摘要与确认

当剩余未知不再影响核心理解或方案时，生成简洁需求摘要。只保留与当前任务有关的项目，可覆盖：

- 真实目标和动机；
- 使用者、场景及已知事实；
- 范围、非目标和关键约束；
- 已验证的假设、证据、矛盾与取舍；
- 期望交付和成功标准；
- 仍需保留但不阻塞理解的未知项。

摘要不得出现推荐方案、技术路线、行动步骤或倾向性措辞。摘要之后只提出一个确认问题，例如：

```text
以上需求摘要是否准确、完整？
```

然后停止并等待回答。用户明确确认后，才能在下一次回复进入方案阶段；用户提出修改时，先完成修改所需的单问题澄清，再重新提交摘要确认。

## 方案阶段

只在需求摘要已被明确确认后给出方案。方案应直接对应已确认的目标、范围、约束、取舍和成功标准，并区分事实、仍需验证的事项与建议。只有确实存在重要取舍时才补充备选路线，不重新引入用户未确认的目标。

如果下一步需要实际修改文件或操作外部系统，仍应按照用户授权和当前环境规则另行判断，不能把需求确认当作执行授权。

## 完成前检查

1. 本轮是否只提出了一个问题，并在问题后停止等待？
2. 当前回答如果仍不清楚，是否留在同一问题而没有跳到下一项？
3. 提问是否在检验动机、假设、证据、矛盾或取舍，而不是暗示答案？
4. 问题是否简短、中立、自然，没有把建议包装成疑问？
5. 用户明确确认需求摘要前，是否完全没有方案、建议、倾向或行动步骤？
6. 是否只询问真正影响理解或方案的内容，而没有机械走完固定清单？
