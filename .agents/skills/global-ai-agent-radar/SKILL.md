# 全球 AI Agent 增量雷达

## 目标

识别最近真正发生的新增变化，并回答：

- 相比此前能力或行业状态，增量在哪里；
- 是否影响 AI Agent 的产品形态、工程实现或交付成本；
- 是否影响企业应用、商业化或行业竞争；
- 技术负责人、产品负责人、业务负责人或创业者是否需要采取行动；
- 后续应使用哪些可验证指标持续观察。

覆盖产品与用户体验、Agent 工程架构、模型工具调用、浏览器与计算机操作、代码执行、多 Agent 协作、记忆与长期任务、MCP 与连接器、企业及垂直应用、开源生态、商业化、融资并购和竞争格局。

## 适用场景

- 生成每日或临时的全球 AI Agent 增量雷达；
- 评估某家公司、产品、技术方向、行业或地区近期是否出现实质变化；
- 为产品规划、技术选型、企业落地、竞争分析或创业判断提供近期信号；
- 在大量报道中核验时间、合并重复事件并筛出真正值得关注的变化；
- 在用户明确要求时，核验并维护结构化观察池。

## 不适用场景

- 汇总所有 AI 新闻、热搜或社交媒体讨论；
- 仅按媒体声量、公司知名度或融资金额制作榜单；
- 编写缺少近期增量要求的长期行业综述；
- 将未经核实的传闻、营销说法或演示视频包装成确定事实；
- 在证据不足时预测价格、投资回报或公司成败；
- 未经用户明确要求自动修改结构化观察池。

## 输入与默认值

- 默认研究范围：最近 72 小时；重点检查最近 24 小时。
- 背景窗口：仅在解释增量时补充最近 1–2 周背景，不把背景旧闻当作新事件。
- 默认地区：全球。
- 默认语言：简体中文。
- 默认读者：技术负责人、产品负责人、业务负责人和创业者。
- 默认观察池模式：研究模式，只读使用观察池并输出调整建议。
- 可选输入：公司、产品、项目、地区、行业、主题、时间范围、时区、读者类型、输出语言和观察池模式。
- 用户明确指定上述输入时，优先采用用户要求；仍需标明实际研究截止时间与时区。

## 观察池工作模式

### 研究模式（默认）

- 以只读方式使用 `assets/watchlist.csv` 发现池内对象，同时执行开放搜索。
- 报告可以提出升级、降级、暂停、剔除或新增建议，并说明证据与建议字段值。
- 不得在生成日报或专题研究时自动修改观察池，也不得因对象不在池内而排除或降分。

### 维护模式

仅当用户明确要求维护或更新观察池时进入：

1. 读取观察池管理规则和当前 CSV；
2. 逐项核验对象身份、官方来源、分类、状态、调整理由和复核日期；
3. 只应用证据支持且属于用户要求范围的变更，不根据单次报告热度批量调整；
4. 修改后运行仓库校验和测试，并查看 `git diff`；
5. 未经用户明确要求，不提交或推送变更。

## 报告模式与分类门槛

`credibility`（信息可信度）是第 6 个评分维度，计入 30 分总分；`confidence`（判断置信度）是位于 `scores` 外的分类字段，不计入总分。两者含义不同，不要求一一映射。始终以六项评分之和重算总分，并按以下优先级分类：

1. `credibility` 为 0–1 分：排除出最终事件清单。
2. `confidence=low`：作为待验证信号，高总分不能覆盖此规则。
3. `credibility` 为 2 分：作为待验证信号，不受总分和 `confidence` 影响。
4. 重算总分 24–30 分、`credibility` 至少 3 分且 `confidence` 为 `high` 或 `medium`：重点事件。
5. 重算总分 18–23 分、`credibility` 至少 3 分且 `confidence` 为 `high` 或 `medium`：一般重要事件。
6. 重算总分低于 18 分、`credibility` 至少 3 分且 `confidence` 为 `high` 或 `medium`：只有执行 Agent 判断值得继续验证时才保留为待验证信号。

- **模式 A：有重点事件。** 最终条目中至少有一个重点事件。
- **模式 B：无重点事件模式。** 临时 JSON 非空但没有重点事件；必须写“今天没有重大突破”，并如实保留一般重要事件和少量待验证信号。
- **空结果状态。** 临时 JSON 为 `[]`，表示没有任何值得写入报告的最终条目；使用更短报告，不生成事件或信号章节。

是否值得验证属于执行 Agent 的研究判断。校验器只对已经决定保留的条目执行结构检查和确定性分类，不得为了通过校验而把低价值候选写入临时 JSON。

## 执行工作流

1. **确定研究边界**：确认当前日期、时区、截止时间和研究起点，分别标出 24 小时重点窗口与 72 小时默认窗口。
2. **明确关注方向与工作模式**：列出重点主题、地区、行业及读者；默认使用观察池研究模式，只有用户明确要求时才进入维护模式。
3. **读取观察池并开放发现**：完整或全球雷达以只读方式读取结构化观察池，同时按能力、行业、地区和生态关系进行开放搜索。
4. **搜索候选事件**：记录候选主体、事件、来源和候选时间；不要在此阶段为了通过数据校验而提前丢弃线索。
5. **寻找原始来源**：优先定位官方公告、产品文档、代码仓库、论文、财报或监管文件；媒体报道只作背景或独立验证。
6. **核验时间**：分别确认来源发布时间、事件实际发生时间和功能可用时间，判断事件是否落入研究窗口。
7. **识别旧闻重发**：追溯最早可验证记录，排除文章更新、转载、摘要和旧内容重新传播造成的伪增量。
8. **合并重复报道**：围绕同一主体、能力、发布阶段和实际事件建立事件簇，按去重策略区分新事件、新证据与新阶段。
9. **拆分陈述类型**：为每个候选项分别记录事实、支撑证据、分析推断和行动建议，不得混写。
10. **评估重要性**：按 30 分制对新颖性、产品、工程、企业与商业化、竞争与生态、可信度评分，并记录理由。
11. **过滤并确定最终条目**：应用分类优先级，确定最终准备写入报告的重点事件、一般重要事件和少量待验证信号；是否保留低分信号由执行 Agent 判断，删除其他低价值事件。
12. **分析影响**：说明产品形态、工程成本与交付、企业采用与商业化、竞争格局四方面中真正受到影响的部分；无证据的方面明确不作判断。
13. **提炼观察指标**：为每个最终条目给出可验证指标、数据来源、观察期限或触发条件。
14. **校验最终条目**：按事件数据契约，只把最终准备写入报告的事件和观察信号写入仓库外的临时 JSON，不校验所有搜索候选；没有最终条目时写入 `[]`。执行环境可运行本地脚本时，以 Skill 目录为基准运行 `python3 scripts/validate_events.py <events.json>`；出现错误时修正数据或排除条目。警告由执行 Agent 复核：确认是否需要补充指标、修正时间或在报告中保留限制，不默认要求用户人工介入。无法运行脚本时，按数据契约和脚本定义执行同等人工检查。
15. **生成增量雷达**：按报告模式读取对应示例并使用报告模板，结论先行，按重要性而非热度排序。
16. **执行最终检查**：逐项核对时间、来源、去重、评分、可信度门槛、事实与推断分离、观察池模式、语言和链接；删除不能通过检查的内容。

## 输出要求

- 开头写明研究截止时间、时区、覆盖窗口、地区、重点方向和面向读者。
- 先给出总体判断，再列重点事件和一般重要事件；每项包含事件事实、相对增量、证据与可信度、影响判断、评分及后续指标。
- 所有重要事实提供可直接访问且能支撑该事实的来源链接，并区分事件发生时间与报道时间。
- 推断使用“这表明”“可能意味着”等明确措辞；建议说明适用对象、行动条件和风险。
- 默认使用简体中文；公司名、产品名、项目名和技术标识保留官方名称。
- 使用普通无重点事件模式或空结果状态时明确写：**今天没有重大突破。** 普通模式如实保留一般重要事件；空结果状态不生成空事件章节。两者都不得用低价值新闻填充。
- 研究模式中的观察池调整只能作为建议，不得暗示 CSV 已被修改。

## 硬性工作规范

- 原始来源优先；二手来源只用于补充背景和独立验证。
- 不得把路线图或未来规划写成已实现能力，不得把小范围测试写成全面上线。
- 不得把营销表述、演示视频、基准领先、媒体数量或融资金额直接等同于真实能力或重大影响。
- 未经核实的传闻不得成为核心结论；信息冲突或无法核实时必须降级表达或排除。
- 同一事件只计一次，不因重复报道增加评分或篇幅。
- 每条结论都必须能追溯到证据；没有证据时明确标为推断，不得补造事实。
- 不写入 API Key、Token、Cookie、密码、私人数据或内部资料。
- 不为追求数量降低收录门槛，也不强行覆盖所有方向。
- 不把事件校验脚本的通过结果当作研究事实正确、来源可靠或评分合理的证明。
- 不在研究模式自动修改观察池；维护模式的写入范围不得超出用户明确要求。
